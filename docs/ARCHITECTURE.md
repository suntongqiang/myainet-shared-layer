# 架构

## 一句话

> **逻辑上一个真相（git commit hash），物理上多份副本（镜像仓）。
> 一致性不靠「放在一起」，靠「校验」和「纪律」。**

## 为什么不是"放在同一个地方"

"放同一个地方"能消除**不一致**，但会引入**不可用**：那一个地方挂了 / 连不上，全网读写全停。
对"多台机器、跨网络、有人在路上信号很差"的场景，这是**更糟**的故障模式。

两个方案都会坏：

| 方案 | 坏在 |
|---|---|
| 单点存储 | **不可用** —— 那台挂了全停 |
| 多副本无校验 | **不一致** —— 静默分叉，且不报错 |

**本方案选择：多副本拿可用性 + 端到端校验拿一致性。**

## 为什么 git 是合适的底座

关键的认知：**N 个镜像仓不是 N 份不同的数据，是同一份内容的三份缓存。**
git 的**内容寻址**（commit hash == 内容的密码学摘要）天然保证了"同一 hash ⇒ 同一内容"。

所以要做的只有两件事：
1. 让所有副本收敛到**同一个 hash**（同步）
2. 让所有消费者**确信自己就在那个 hash 上**（校验）

## 拓扑

```
逻辑真相 = git commit
   │
   ├── mirror A（bare，数据盘）   ← 任意节点可读写
   ├── mirror B（bare，数据盘）
   └── mirror C（bare，数据盘）   ← 热备
        │
        ├── machine 1 工作副本    ← origin 指向最近的镜像
        ├── machine 2 工作副本
        └── machine 3 工作副本
```

- 每个节点**能读写任意一个镜像** → 任一镜像机故障，其余照常。
- 每个工作副本的 `origin` 指向**自己最近的那个镜像**（拿到本地速度 + 可用性）。
- **所有副本的内容由同一个 commit hash 定义** —— 这就是"逻辑上的同一个地方"。

## 三个必须自动化的事实

| 要确认的事实 | 工具 | 失败时的表现 |
|---|---|---|
| 所有镜像是否收敛到同一 commit | `shared-sync.sh` | 推送侧计数 |
| **所有工作副本是否真的在那个 commit 上** | **`verify-live.sh`** | 报警 + 非零退出 |
| 新写的条目是否与既有编号冲突 | `next-mem-id.sh` + `check-integrity.sh` + pre-commit | 拒绝提交 |

**中间那一行是整套方案的关键。** 没有它，前一行会给出虚假的安全感。

## 写入路径（消除编号冲突）

```
agent ──► inbox/<agent>-<时间戳>.md      （唯一写入通道，文件名天然不冲突）
                │
                ▼
         唯一 promoter（比如每晚 01:00 的复盘任务）
                │  分配正式编号 mem-NNNN
                ▼
         canonical：memory/mem-NNNN.md + INDEX.md
```

- **写**：任何 agent 只写自己的 inbox 文件 —— **不需要协商，不可能冲突**。
- **晋升**：由**唯一的** promoter 分配编号 —— 单点分配，冲突在结构上不存在。
- **取代**：新条目若取代旧条目，旧条目 `status: superseded` + `superseded_by`，**永不删除**。

## 与其它方案的取舍

| 方案 | 为什么不选 |
|---|---|
| Obsidian Sync | 付费插件；只是换一种传输；冲突处理生成 "conflicted copy"，无合并/无历史回滚 |
| Syncthing | 解决"文件怎么过去"，不解决"多写者怎么不打架"；冲突产物是 `.sync-conflict` 副本文件 |
| 云盘目录 | 同上，且冲突处理更不透明 |
| CRDT（Yjs/Automerge） | 对几 MB Markdown、低频写入，复杂度收益不划算 |
| 单点数据库服务 | 真能根治，但把"分配"变成单点运行时依赖，对 5 台机器几 MB 文本属过度工程 |

**Obsidian 的位置**：它是**给人开的窗**（双链 / 图谱 / 搜索），不是**同步的桥**。两者不冲突，各司其职。
