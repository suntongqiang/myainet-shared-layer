## 结论（诚实）

**统计：他们 18 项记忆引擎能力 —— 我们 ✅ 2 项、🟡 9 项、❌ 7 项。**

### 没有"全部覆盖"，而且**不该**全部覆盖

理由：我们缺的那 7 项 ❌（语义向量、概念图谱、SQLite 增量索引、自动归类、
bigram 去重、访问计数、LLM 会话提炼）**全是"记忆引擎"内部实现**，
他们已投入大量工程并有测试。**我们重造一遍是浪费，且做不过他们。**

**我们独有的 6 项（19~24）他们完全没有**，而且这些是**多机场景的刚需** ——
它们不是"锦上添花"，是"没有就会静默坏掉"。

### 正确做法：**叠加，不是取代**

```
┌───────────────────────────────────────────────┐
│  unified-agent-memory  ← 记忆引擎（他们强）     │
│  检索 / 向量 / 图谱 / 遗忘 / 去重 / 会话提炼     │
├───────────────────────────────────────────────┤
│  myainet-shared-layer  ← 多机一致性（我们强）   │
│  同步 / 活副本校验 / 编号分配 / 凭据闸 / 故障库 │
└───────────────────────────────────────────────┘
```

### 若还要继续补，按性价比排序（建议）

1. **给 `inbox-submit.sh` 加凭据拒绝**（他们是在"提交时"拒，我们只在"提交 git 时"拒）—— 半天工作量，收益高。
2. **用 SQLite FTS5 做真索引**（`sqlite3` 在 Python 标准库里，我们已有 Python）—— 替换 grep，检索质量和规模都上一个台阶。
3. **加访问计数**（`memory-search` 命中时记一行）—— 有了它，`memory-stale` 才能用他们那套 `salience × decay + 强化` 公式。
4. **其余（向量/图谱/LLM 提炼）建议直接接他们的引擎**，不重造。
