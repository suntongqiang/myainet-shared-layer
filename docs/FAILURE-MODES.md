# 故障模式库（全部来自真实事故）

> 本文件是这个项目**最值钱的部分**。下面每一条都是真实发生过的，不是推演。
> 造这套共享层的人踩过的坑，你不必再踩一遍。

## FM-01 ★★★ 半截迁移：能推、拉不到，且**没有任何报错**

**症状**：主控机推到新镜像显示成功（`pushed_remote=2/3`），但某台机器的活副本**永远收不到新内容**。
`git log` 里找不到主控推的 commit。

**根因**：迁移只做了一半 —— 建好了新镜像仓 + 写了同步脚本，**但没有改各机活副本的 `git remote origin`**。
那台机器的 origin 还指着**旧的单源仓**。它的同步任务照样在跑、照样在推，所以一切"看起来正常"。

**为什么可怕**：**方向是单向的**。机器 → 镜像的推送能走，镜像 → 机器的拉取不走。
两个方向各自"成功"，合起来是断裂，而**没有任何一方会报错**。

**对策**：
1. 迁移必须**成对**：建镜像 + **改所有消费方的 origin**。
2. 同步脚本**只报推送侧是不够的** —— 必须加 `verify-live.sh` 逐台校验活副本 HEAD。
3. 把"活副本是否真的更新"变成**可检测事实**，而不是信念。

**教训**：`pushed_remote=2/3` 这种**单侧指标**会被所有人读成"同步好了"。
**只测了一半的链路，却当成全链路** —— 这是隐形态故障的标准剧本。

## FM-02 ★★★ 编号撞号：多机并发分配同一个 ID

**症状**：两台机器各自创建了 `mem-0212.md`，内容完全不同（一台写 ERP、一台写量化）。
合并时 8 个文件全部冲突。

**根因**：编号按「**数本地 INDEX 最大值 +1**」分配。每台机器只看得到**自己那条线**，
看不到别人已经占了哪些号 —— 并发下**必撞**。

**历史**：同一类事故发生过至少两次（`mem-0184` 撞号、`mem-0212–0219` 撞号）。

**对策（三层，建议全上）**：
1. **分配器**：`next-mem-id.sh` 跨**所有可达镜像**取最大编号 +1（禁止数本地）。
2. **结构消除**：per-agent 时间戳 inbox 作为唯一写入通道（`inbox-submit.sh`），
   由**唯一的 promoter** 分配正式编号（`promote-inbox.sh`）。文件名天然不冲突。
3. **守卫**：`hooks/pre-commit` 拒绝引入重复编号的提交。

**教训**：**架构解决不了多写者的编号冲突，只能靠"唯一分配点"或"结构上不共享命名空间"。**

## FM-03 ★★ 单点仓：一台机器挂掉，全网读写全停

**症状**：唯一的 bare 仓宿在 A 机。A 机一挂，五台机器**推不进也拉不动**。

**对策**：建 N 个互为镜像的 bare 仓，每个节点都能读写任意一个。
**关键**：镜像仓必须放在**数据盘**，不能放系统盘 —— 系统崩了镜像跟着一起没。

**教训**：可用性和一致性是一对取舍。**多副本买的是可用性，校验买的是它的一致性。**

## FM-04 ★★ 各机活副本有未提交改动 → 拉取被挡

**症状**：`git pull` 报 `Your local changes would be overwritten` 或
`untracked working tree files would be overwritten`，拉到一半失败，活副本变成 17 个脏文件。

**对策**：拉取**之前**先 `git stash push -u -m "autofix-<时间戳>"`
（`-u` 连未跟踪文件一起收），拉完**不自动 pop** —— 让那台机器自己决定何时恢复。
**永远不要**用 `git checkout .` / `reset --hard` 去"清理"别人的未提交工作。

**教训**：自动化同步脚本必须假设**工作区是脏的**，并且**保命优先于干净**。

## FM-05 ★★ 单侧比对：PowerShell 输出带 `\r` 导致校验假失败

**症状**：写好的活副本校验脚本，**所有机器全部报 STALE**，但人工一看 HEAD 都一致。

**根因**：Windows PowerShell 的输出行尾是 `\r\n`。ssh 管道里取到的值是 `"4ccf20a\r"`，
和 `"4ccf20a"` 字符串比对**永不相等**。

**对策**：跨平台取文本一律 `tr -d '\000\r'`。

**教训**：**校验脚本本身也会说谎。** 上线校验器时，必须先拿"已知正常"的场景验证它**不误报**。

## FM-06 ★ 子串误判：新名字包含旧名字

**症状**：origin 判断逻辑把所有机器都标成"仍指向旧仓"。

**根因**：旧仓叫 `shared-git.git`，新仓叫 `myainet-shared-git.git` ——
**新名包含旧名子串**。用 `case "$url" in *shared-git.git)` 先匹配，新仓也被命中。

**对策**：`case` 分支**先匹配更具体的模式**（先判 `*myainet-shared-git.git`），
且不要用 `[ "$x" != *glob* ]` —— **`[ ]` 不做通配符匹配**，那是个静默恒真的表达式。

## FM-07 ★ 前导零被当八进制

**症状**：编号分配器算出 `NEXT=mem-0152`，而实际最大编号是 `0227`。

**根因**：bash 的 `$((max+1))` 把 `0227` 按**八进制**解释（=151），加一得 152。

**对策**：算术前强制十进制：`$((10#$max + 1))`。

## FM-08 ★★ 冲突标记被当成"已解决"提交进去

**症状**：仓库里出现带着 `<<<<<<<` / `>>>>>>>` 的 Markdown 文件。

**根因**：`git add -A` 会把**仍含冲突标记**的文件标记为已解决，然后就能提交了。

**对策**：提交前扫一遍冲突标记（`check-integrity.sh` 内含此检查）；
能用 `git add <具体文件>` 就不要用 `git add -A`。

## FM-09 ★ 长任务挂在 ssh 会话上，会话一断任务就被回收

**症状**：远程起的长任务（几十分钟）跑一半就没了，日志停在中间。

**对策**：长任务要么**用 ssh 前台持有**（并由调用方后台化），
要要么**注册成计划任务**（`schtasks`）让它在机器上独立存活。
**不要**用 `Start-Process` 起 detached 子进程 —— ssh 会话结束时它会被回收。

## FM-10 ★ 只改文档没改消费方：约定写在纸上了，机器不知道

**症状**：协议文档里明明写了"各机 origin 指向新镜像"，但没人执行，于是 FM-01 发生。

**对策**：**能被机器校验的规则**才写进文档；否则给一个**一键脚本**并把它的输出接到同步流程里。

**教训**：文档不是约束，**可执行的校验才是约束。**

## FM-11 ★★★ 「索引写了，文件忘了」—— 悬空索引活了 8 天没人发现

**症状**：`INDEX.md` 里有 `mem-0130` 一行（内容完整、看着正常），**但 `memory/mem-0130.md` 文件从来不存在**。
全库浏览、全文检索都正常，**没有任何地方会报错**。

**根因**：提交时只 `git add` 了 `INDEX.md`，忘了 add 那个新建的条目文件。
一次真实的提交（`d70695e`）就这样：`memory/INDEX.md` + `DAILY/...` + `METHOD_LAWS.md` 三个文件进去了，
**条目本体漏在外面**。

**为什么危险**：它看起来"一切正常"。索引行的内容还在，所以**连读的人都发现不了** ——
直到有人真去 `open` 那个条目。**这是纯静默的数据丢失。**

**对策**：`check-integrity.sh` 的 §4 双向比对（INDEX ↔ 目录）。
**本次就是它抓出来的** —— 挂了 8 天的悬空行，体检一跑就现形。

**恢复**：内容往往没真丢 —— 它可能同时落在 `DAILY/`、`METHOD_LAWS.md` 或别的已提交文件里。
**先去 git 历史里找，再决定是重建还是删行。**

## FM-12 ★★★ 规则写成了文档 ≠ 规则存在（本项目诞生的真正原因）

**时间线**（真实事故的两次发生）：

| 时间 | 事件 |
|---|---|
| 2026-09-20 | 写 `mem-0128` 前没查远端编号 → 撞号 → rebase 冲突 → `git add -A` 把冲突标记提交进共享层（`mem-0130` 记录） |
| 2026-09-20 | **制定了方法律 #44/#45**："写记忆前必须 pull 并取远端 max+1"、"`git add -A` 会静默提交冲突标记" |
| **2026-09-28** | **同类事故原样复发**：写 `mem-0212–0219` 前又没查远端编号 → 与另一台机器的 `mem-0212–0219` **全部撞号**（8 条文件冲突） |

**根因**：`#44/#45` 当时**只写成了文档**。文档不会拦住任何事 ——
**8 天后没有人记得它，包括写文档的那个 agent 自己。**

**对策（本项目的存在理由）**：把每一条规则都变成**机器能判定的检查**：

| 规则 | 文档形态（无效） | 可执行形态（有效） |
|---|---|---|

| 索引进文件 | 无 | `check-integrity.sh` §4 双向比对 |
| 所有机器都同步了 | 无 | `verify-live.sh` |

> **文档不是约束，可执行的校验才是约束。**
> 如果你正打算把一条规则写进 README 然后收工 —— 请先问：**有没有一个脚本，能在违反时让人当场撞墙？**

## FM-13 ★★★ 安装器"假成功"—— 本项目的安装脚本自己犯了这个病

**症状**：`install-hooks.sh` 打印 `HOOK=OK`，但钩子**根本没装上**，后续提交畅通无阻。

**现场**：
```
cp: cannot create regular file '.../.git/hooks/pre-commit': No such file or directory
chmod: cannot access '.../.git/hooks/pre-commit': No such file or directory
HOOK=OK                      ← 仍然报成功
```

**根因**：脚本 `cp` 之后**没有检查退出码**，直接打印了成功。
（触发条件：某些 git 环境 `git init` 不创建 `.git/hooks/`，
本例就是 `templates not found` 导致 hooks 目录缺失。）

**为什么这条特别值得记**：**这个项目的存在就是为了消灭"失败却报成功"** ——
而**它自己的安装脚本犯了同一个病**。这恰好说明这类 bug 有多顽固：
它不是"粗心"，而是**"我没有验证我声称的结果"**这个习惯。

**对策（三件套，缺一不可）**：
1. `mkdir -p` 目标目录（别假设它存在）；
2. **每一步检查返回值**，失败即 `FAIL` 退出；
3. **装完必须回读验证**（`[ -x "$HOOKDIR/pre-commit" ]`）——
   不能只信 `cp` 的退出码，更不能什么都不信就打印 OK。

> **凡是打印"OK / 成功 / 已同步"的地方，都必须有一条"回读验证"紧跟其后。**
> 没有回读的成功报告，就是下一次 FM-01。

## FM-14 ★★★ 一枚明文 Token 在共享层里躺了 19 天，没人发现

**症状**：一个技能文件里**硬编码着 GitHub Token**。它随共享层同步到 5 台机器，
**没有报错、没有告警、没有影响任何功能** —— 直到有人为了别的事去翻那个文件。

**事故经过**：
某技能为了"一键发布到 GitHub"的便利，把发布用的 Token 直接写进了 HTML 的默认值里
（输入框 `value=` 和 JS 常量各一处）。Token 权限是 **`repo` 全仓**，
意味着它能读写该账号下**所有**仓库，包括一个私有仓。

**为什么它比想象中危险**：
1. **共享层是会被复制的** —— 它躺在那里，跟着镜像走到每一台机器。
2. **它在 git 历史里** —— 就算删掉文件里的那行，**历史里那串依然可读**，
   所以"删文件"根本不是修复。
3. **它是"便利"引入的** —— 不是为了偷懒，恰恰是**为了功能好用**。

**唯一的正确修复**：**轮换（revoke + 新建）**。文件清理只是附加动作。

**对策（三层，已全部落地）**：
1. `check-credentials.sh` —— 扫描明文凭据（GitHub/AWS/Slack/OpenAI/私钥/通用 `token=` 形态），
   命中即红色输出**并自动脱敏**，退出码非零。
2. 接进 `check-integrity.sh` §6 —— **体检就会带出来**。
3. 接进 `hooks/pre-commit` —— **提交当场被拒**。

**教训**：
> **"方便"是最常见的凭据泄露路径。**
> 任何"预填好、直接点就能发"的设计，都要问一句：**这里填的是不是密钥？**
> 而且 —— **密钥一旦进过版本控制，轮换就是唯一解**，别再想着删文件。

## FM-15 ★★★ 一个 BOM 让整台机器的出站 ssh 全废（而且是自动化脚本干的）

**症状**：某台机器的 **git 同步全线失败**，报的错却指向配置：
```
FETCH_FAIL .../.ssh/config: line 1: Bad configuration option: \357\273\277#
```
`\357\273\277` 就是 **UTF-8 BOM（EF BB BF）**。
BOM 出现在**第 1 行**意味着整个文件被重写时带了 BOM —— OpenSSH **不认 BOM**，
于是**该机所有出站 ssh 全部失效**（拉镜像、连别的机器，全挂）。

**这是怎么发生的**：给该机追加一段 GitHub 的 ssh 配置时用了
**PowerShell 的 `Add-Content -Encoding UTF8`** —— 在 Windows PowerShell 5.1 里
它会写出 **带 BOM 的 UTF-8**。一个"顺手加两行配置"的动作，
**打掉了整台机器的出站 ssh**。

**同一动作的第二个坑**（同一次事故里一起出现）：
配置里写了**中文注释**，结果 **`Host github.com` 被吞进了注释行**
（写文件时换行丢失，正是"中文注释吞下一行"的老问题）——
即使没有 BOM，那段配置也是坏的。

**对策（两条硬规则）**：
1. **改 ssh/ssh 相关配置文件一律"先读全文 → 内存里改 → 整体 WriteAllText"**，
   且必须用 **无 BOM** 写法：
   ```powershell
   [IO.File]::WriteAllText($p, $text, [Text.UTF8Encoding]::new($false))
   ```
   **不要用** `Add-Content -Encoding UTF8` / `Out-File -Encoding utf8` 往这类文件追加。
2. **这类配置文件只写 ASCII**（注释也用英文）——
   中文注释在"写文件"链路上极易吞换行，而且回显常被 GBK 弄成乱码，**排障时连自己写的什么都看不清**。

**修法**：
```powershell
$txt = [IO.File]::ReadAllText($p).TrimStart([char]0xFEFF)
[IO.File]::WriteAllText($p, $txt, [Text.UTF8Encoding]::new($false))
```
改完**先 `ssh -G <host>` 自检**（不联网，只验证配置可解析），再去连真实主机。

**教训**：
> **改别人机器的关键配置文件，本身就是"高风险写操作"。**
> 而这个事故最讽刺的地方是 —— 我加那段配置，**正是为了"修好同步"**。
> 把它记下来，是因为它同时踩中了两条本项目反复强调的东西：
> **失败要能当场发现**（这次是 git 报出来的），以及
> **自动化脚本写文件必须用确定的编码**。

## FM-16 ★★ 令牌藏在 `.git/config` 的 remote URL 里 —— 扫描器看不见

**症状**：我们在共享层里清掉了 3 处明文凭据，以为收拾干净了。**其实还有第 4 处**：
某台机器的克隆里，remote 地址是
```
https://suntongqiang:ghp_xxxxxxxx@github.com/suntongqiang/mingpian-ecard.git
```
**令牌明文写在 `.git/config` 中。**

**为什么危险 / 为什么之前没发现**：
1. `.git/config` **不会被提交**，所以"扫仓库/扫历史"的思路永远看不见它 —— 但**它在磁盘上，且会被备份、会被整目录复制、会被同事顺手拷走**。
2. 我们的 `check-credentials.sh` 只扫**你指定的那个根目录**（共享层），
   而这台机器上的克隆在 `F:\harness\` —— **根目录之外**。
3. 更隐蔽的是：**它让"推送能work"看起来理所当然**，于是没人去想"凭据到底存在哪"。
   直到令牌被吊销，推送突然失败，才暴露出它的存在。

**对策（三层，缺一不可）**：
1. **永不用 URL 内嵌凭据**。要 HTTPS 就走 **Credential Manager**；
   在 Windows 上把 GCM 的存储设为 **DPAPI 加密**：
   ```powershell
   git config --global credential.credentialStore dpapi
   ```
   然后 `git credential approve` 录入一次（密文落盘，无明文文件）。
2. **扫描器要扫"机器"而不只是"仓库"**：把 git 仓库的 `.git/config` 也纳入检查：
   ```bash
   git config --get-regexp '^remote\..*\.url$' | grep -E '://[^/@]+:[^/@]+@'
   ```
3. **推送前不要只看"成功"** —— 要能回答"凭据存在哪、是否明文"。

**教训**：
> **"凭据在哪儿"必须是一个能回答的问题。** 如果答案是"反正推送能用"，
> 那就说明**没人知道它在哪** —— 这正是它会在那里躺 19 天的原因。

## FM-17 ★★ `.gitignore` 白名单漏掉凭据的「备份变体」—— 轮换本身会制造新的明文副本

**症状**：我们以为凭据防线已经收口（FM-14 立了 `.gitignore` 规则）。
实际磁盘上躺着一个 **`uumit-auth.json.dead-20260929.bak`** —— 上一轮轮换时留下的旧密钥备份。
`git status` 把它显示为 **未跟踪（`??`）**，也就是说：

> **再敲一次 `git add -A`，它就会被提交、被推到所有镜像、被同步到每一台机器。**

**为什么 `.gitignore` 没挡住**：当时的规则写的是

```
skills/*/memory/*auth*.json
```

文件名是 `uumit-auth.json.dead-20260929.bak` —— **它确实以 `*auth*` 开头，但结尾不是 `.json`**。
`*auth*.json` 要求模式**匹配到路径末尾**，而后缀 `.dead-20260929.bak` 把匹配顶掉了。

**这是 FM-13（假成功）的同类病**：规则看起来很合理、并且"我们检查过了"，
但**规则从没被真正测试过** —— 没有人造一个假文件去验证它会否被忽略。

**对策（四条）**：
1. **按前缀忽略，不要锚定后缀**：写成 `skills/*/memory/*auth*`（去掉 `.json`），
   这样 `.bak` / `.dead-*` / `.old` / `-2.json` 统统被覆盖。
2. **再加一道后缀网**：`skills/*/memory/*.bak`、`skills/*/memory/*.dead-*`。
3. **必须验证守卫真的生效**（可复制的动作）：
   ```bash
   cd <共享层>
   touch skills/<任意技能>/memory/uumit-auth.json.dead-test.bak
   git status --short skills/<任意技能>/memory/    # 必须不出现该文件
   rm -f skills/<任意技能>/memory/uumit-auth.json.dead-test.bak
   ```
4. **更好的做法是根本不留备份**：已撤销的密钥没有任何使用价值，
   留着它是**纯风险、零收益**。轮换完直接 `rm`，而不是 `.bak` 归档。

**教训**：
> **"我加了 .gitignore"不等于"它被忽略了"。** 安全规则和代码一样，**没测过就等于没写**。
> 更反直觉的一点：**每一次"安全地换钥匙"的动作，都会顺手生产一份新的明文副本** ——
> 轮换流程必须把自己产生的中间产物也算进威胁模型。

```bash

```

4. 拉取：被 5 个未跟踪文件 + 6 个已修改文件挡住 → **先备份未跟踪文件、再 `git stash` 保住本地改动**，

`git pull` 报"不是内部或外部命令"。必须用全路径：

**任何在该机跑的定时同步任务，如果用的是裸 `git`，都是静默失败。**

**教训**：
> **"少一行"可以比"多一行"危险得多。** 结构型配置文件（ssh config / sudoers / nginx）里，
> 缺失的定界符会把**局部规则变成全局规则**，而且**文件读起来完全正常**。
> 这类问题的正解是**问工具最终生效值**（`ssh -G`），而不是读文件推理。

## FM-24 ★★★ 远程执行用 `-EncodedCommand` —— 撞 Windows 8191 命令行上限，报一个完全误导的错

**症状**：一整个下午，从手机往 **cunchu** 发的每一条 "读 stdin + 执行" 的远程命令**全部失败**，
报的是 `ssh(shim): Timed out while waiting for handshake` 或干脆**零输出** ——
看起来像网络抖动，于是反复重试，白耗几小时。

**根因**（同类项目已归档，且给了决定性证据）：`powershell.exe -EncodedCommand <base64>` 在 Windows 上受
**8191 字符命令行上限**约束（cmd.exe / CreateProcess）。而 **UTF-16LE 的 base64 会把脚本膨胀约 2.67 倍**：
一个 ~3,100 字符的脚本 → ~8,000+ 字符命令行 → **超限** → 远端回 `The command line is too long.`、
**stdout 为空** → 上层只能报一个与真实原因无关的错误。

**决定性证据（与我们实测一致）**：**同一份脚本**
- 走 `-EncodedCommand` → 失败、stdout 空
- 走 **`-File <路径>`** → 成功
→ **问题在传输方式，不在脚本、不在网络。**

另外：cunchu 的 `HKLM\SOFTWARE\OpenSSH\DefaultShell` 被改成 PowerShell（`DefaultShellCommandOption=-c`）之后，
**长 `-EncodedCommand` 必失败**；同机上 `-Command` / 普通命令 / `-File` 都正常。

**对策（三条，按优先级）**：
1. **★优先 `-File` staging**：把 `.ps1` 写到远端临时文件，再 `powershell -NoProfile -ExecutionPolicy Bypass -File <path>`。
   —— 同类项目推荐的正是这条："最小的改动、脚本原文不变、避开单行 argv 上限"
2. **`-Command` 或 stdin（`-`）传输**：短脚本可用；长脚本不要走命令行
3. **要 `-EncodedCommand` 就必须先量长度**：`base64(utf16le(script)).Length + 固定开销 < 8191`，
   **超了就 gzip+b64 或改 `-File`**

**★方法论（这条比故障本身值钱）**：
> **"报网络错"时要先怀疑"我发的命令根本没被正确执行"。**
> 我们这次的表现是"ssh 握手超时"，而真因是**命令行太长** —— 一个**完全无关**的错误面。
> 判据：**换一种传输方式（`-Command`/`-File`）若立刻好，就不是网络。** 这一条 5 秒钟就能验，我却反复重试了几小时。

**同类项目归档**：`NousResearch/hermes-agent` issue **#106716**
*"Desktop SSH to Windows remote fails: probe command line exceeds Windows 8191-char limit"*（open，P2）
https://github.com/NousResearch/hermes-agent/issues/106716

## FM-25 ★★ 「写记录」这一步自己会栽：一个高声失败、一个**静默丢内容**

**症状**：明明是"把结论永久记下来"这个最不该出错的环节出事。2026-09-30 一次会话里连撞两个，
**其中一个不报错**。

### 实例 A：Android 挂载点上，原子写入用硬链接 → `EACCES`（**高声失败，好查**）

本机（dsh-mobile）用 DSH 的 `write` 工具写 `~/.dsh/_shared/reports/trading/xxx.md` 失败：

```
EACCES: permission denied, link '.../.xxx.md.tmpdir/xxx.md.tmp' -> '.../xxx.md'
```

- 目录本身**可写**（`touch` / `printf > file` 都成功，`ls -ld` 是 `drwx------ u0_a304`）
- 真因：该类实现走**「写临时文件 + 原子 `rename`」**，而 Android 的挂载点（`/data/data/...`，
  FUSE 系）**不允许硬链接** → `link(2)` 直接 EACCES
- **判据（5 秒区分"没权限"还是"实现不支持"）**：在目标目录 `touch probe && printf x > probe2 && rm probe*`。
  **能成功 ⇒ 不是权限问题，是原子写法问题。**
- **对策**：改用 **shell 直写（引号 heredoc）** 或 `python3 -c` 写；把"原子性"让给 git（写完 `git add` 时自然可回溯）

### 实例 B：★**静默**丢内容 —— 双引号里的反引号被 shell 当命令替换执行

用 `echo "... `代码` ..." >> memory/INDEX.md` 追加索引行，内容里含反引号包起来的结论 `F_res ≡ asym_res`：

- 写入**成功**、**退出码 0**、**没有任何报错**
- 实际落盘的是：`**恒等式  证明 stren 项贡献恒为 0**` —— **反引号里的关键结论被吃掉，变成一段空白**
- 唯一线索是 stderr 里一句极易忽略的 `bash: line 65: F_res: command not found`
- 真因：**双引号内**反引号是**命令替换**（`$(...)` 的同义写法），会把内容当命令跑，用其输出替换
  ——与 FM-21（未加引号的 heredoc 吃掉内容）**同一根因的两个面**

### ★合并教训（比两个坑都值钱）

> **要把一段任意文本写进文件时，永远不要让 shell 去"解释"它：**
> **一律用 ①引号 heredoc（`<<'EOF'`）②`python3` 写 ③文件写入工具。**
> **绝不要用 `echo "…"` / `printf "…"` 去写含 反引号、`$`、`\`、`!` 的内容。**

> **写永久记录必须"回读校验"，不能只看退出码。**
> 本次是顺手 `tail -1` 才发现的；若不回读，`INDEX.md` 会带着一条**空白结论**长期留在全网共享层里，
> 比直接报错危险得多。**→ 每次改 `INDEX.md`/记忆文件后回读校验，已在作业清单里固化。**

**与既有条目的关系**：FM-21 记的是"未加引号的 heredoc 吃掉内容"；FM-23 记的是"校验器覆盖面不足"。
本条把两者收口为一条可执行纪律：**写非受控文本 → 引号 heredoc/python；写完 → 回读**。

## FM-26 ★★★ 计划任务**连续两天静默失败**：三个叠在一起的缺陷 + 一个校验盲区

**症状**：盘后复核持仓时才发现 `aquant_gate`（每天 15:40 的全市场门槛扫描 + 日线缓存刷新）
`LastTaskResult = 0x80000003`，**已经坏了至少两天**。日志里**只有崩溃栈、没有任何正常输出**，
全网没有任何告警；同时 `openpos` 的持仓表把一只持仓渲染成 **−100.00%**。

### 缺陷 1：内嵌 V8 的 C++ CHECK 直接 abort 进程（Python 拦不住）
`gate.py:54` 用 `ThreadPoolExecutor(max_workers=10)` 并发刷日线，**多个线程同时构造**
`py_mini_racer.MiniRacer()`：

```
[FATAL:partition_address_space.cc(243)] Check failed: !IsConfigurablePoolInitialized().
```

这是 **C++ 层 CHECK 失败 → abort**，`try/except` 完全无效。返回码 `0x80000003`。
**决定性复现**：10 个线程各 `MiniRacer()` → `rc = -2147483645 = 0x80000003`（与失败任务逐位相同）。

**对策**：`aquant/_v8guard.py` —— 给 `MiniRacer` 的 `__init__/eval/call/execute` 套**全局可重入锁**，
在 `aquant/__init__.py` 里 `install()`。改后同脚本 10/10 通过。
★**推广**：任何「多线程 + akshare/py_mini_racer」的组合都有此雷（本项目另有 2 处 ThreadPoolExecutor）。

### 缺陷 2：把「拿不到数据」渲染成「跌光了」
`openpos.py:118` 只给 `open_df` 的票 + 一个硬编码代码取实时价，而下面的 WATCH 表用
`sp.get(code) or {}` → 拿不到的持仓 `px=0` → `(px/cost-1) = -100.00%`。
**在交易看板里，把「缺数据」显示成「跌 100%」是最危险的一类错。**

**对策**：把要展示的代码**全部**并入取价；兜底链 **实时价 → 缓存最后收盘 → 「—」**，
**任何情况下都不渲染 −100%**。

### 缺陷 3：批量刷新没有墙钟预算
数据源集体失效时（FM 家族另一条：免费高频通道全灭），单只票要 3 源 x 3 次重试十几秒，
全市场 5580 只要一个多小时**且刷不出东西**，把 15:40 的任务拖死。
**对策**：`refresh(..., budget_s=420)` + `--refresh-budget`，超预算后剩余代码空跑返回（「有多少用多少」）。

### ★★校验盲区（本条最值钱）：只问「任务在不在」，不问「它跑成功了吗」
`verify-fleet.sh` 原有 (a)(b)(c) 三项；**(b) 只检查任务是否存在、是否被两台同时启用**，
**从不检查 `LastTaskResult`** —— 于是任务可以带着 `0x80000003` 死两天而校验全绿。
**这是 FM-23「校验器的覆盖面，就是故障的藏身处」的又一例证。**
→ 已补 **(d) 计划任务健康**：逐机取启用中交易任务的 `LastTaskResult` + `LastRunTime`；
非 `0 / 267009(运行中) / 267011(未运行)` 判 FAIL，最近运行 > 5 天判 WARN。

### 顺带两条同源坑
1. **`.cmd` 文件由 cmd.exe 按 GBK 读取**：用 UTF-8 写批处理、里面含中文路径（`金刚`），
   cmd 会把路径解码成乱码 → `cd /d` 失败 → 重定向到不存在的相对目录 →
   任务 `RC=1` 且**一个输出文件都不生成**。**中文路径不要走 .cmd，改 Python 启动器。**
2. **「缓存末日 = 今天」分不清「收盘定稿」和「盘中快照」**：出问题那天的缓存 bar
   `mtime = 14:40:05`（盘中），但所有基于日期的检查都报 `✅ 数据截至 2026-09-30`。
   后果实测：同一只票两源收盘价不一致（13.80 vs 13.70，而同一天的 open/high/low 两源一致）。
   **→ 新的待办：新鲜度判据必须加 finality（是否已收盘定稿）。**

### ★合并教训
> **「没有告警」不等于「一切正常」—— 一个没人看返回码的定时任务，随时可以安静地死上好几天。**
> 任何无人值守任务，都要有一条**独立于任务自身**的存活判据（返回码 + 最近运行时间），
> 而且这条判据必须**写进机群校验器**，否则它只是"文档里的规则"（FM-12）。

### 顺带 3：`Stop-ScheduledTask` **不会杀子进程** → 留下僵尸 python 继续啃网络
本次为绕开坏数据源，我停掉了自己起的临时任务 `AquantPostClose`；但 `Stop-ScheduledTask`
**只停任务、不杀它启动的子进程** —— 那个 python（PID 3964）**继续全市场联网重试**，
累计吃了 **844s CPU**，直到手动 `Stop-Process` 才停。
→ **凡是「停任务」，必须顺手核对子进程是否真的没了**（`Get-Process python` + `StartTime`）。
→ 否则会出现「我明明停了它」与「它还在跑」同时成立的诡异状态，且**两个全市场扫描并行争抢网络与磁盘**。
★附带一个 PowerShell 小坑：**`$pid` 是自动只读变量**，`foreach($pid in ...)` 会静默不生效 ——
要改用 `$procId` 之类。

## FM-27 ★★★ 同一个目录里两套并行缓存 + 「日期新鲜」冒充「收盘定稿」

**症状**：所有报告都写「✅ 数据截至 2026-09-30」，但那天全部结论其实是在**未收盘定稿**的 bar 上算的；
同一只票在同一天有**两个不同的收盘价**（13.80 / 13.70），而没人知道该信哪个。

**事实（2026-09-30 全市场实测）**：
- `_cache/daily/` 下并存 `*_qfq_tx.csv`（5106 只 / 1882 行）与 `*_qfq_sina.csv`（5218 只 / 425 行）
- **4905 只的「最新一根」100% 是 mtime 14:40 的盘中快照，已收盘定稿 0 只**
- 两套**连已定稿的历史日期都不一致**（09-29 为 13.60 vs 13.55）→ **不是同一个序列**

**根因：生产者与消费者错配。**
- 读 `_qfq_tx` 优先：`aquant_panel.py`（日线技术指标）、`openpos.py`
- 写 `_qfq_sina`：`gate.py` 的 `refresh(sources=("sina",))`
→ **每天 15:40 的刷新写的是消费者不优先读的那一套**，于是核心消费者长期读 14:40 的盘中 bar。

**★教训一（可复用）**：
> **「日期是新的」不等于「数据定稿了」。** 盘中任务会往"日线"里写当天未收盘的 bar，
> 而任何只看日期的检查都会放行。
> **且 mtime 不可独信** —— `Copy-Item` 保留 LastWriteTime，批量拷贝能伪造出统一的 14:40。
> → 正解：盘后任务写一个 **marker 文件**（内容=完成的交易日），
> 「已定稿」= marker 日 == 最新 bar 日；**没有 marker 就一律标"未定稿"**。

**★教训二（可复用）**：
> **同一个逻辑对象只能有一份权威副本。** 两台机器上同名文件各自演化（FM-20）是同一个病的另一个面；
> 这里换成了**同一台机器、同一个目录、两套并行文件**。
> 判据：**任何"读的时候挑一个"的代码（`if c not in files or "_tx" in b`），都在掩盖权威副本缺失。**
> 本项目里 `bt_mined.py` 的注释早就写过一次：「硬编码 `_qfq_sina.csv` 会把退市股静默跳过」——
> **同一个坑第二次被踩**，说明上次只修了那一个调用点，没修"该有唯一权威源"这件事本身。

### 顺带 4：**「正在运行」被当成健康** —— 任务挂死 3.5 小时，(d) 却放行
补上 (d) 之后当晚就撞到它没覆盖的那一面：`aquant_gate` 从 19:44 起一直 `Running`，
**CPU 冻结在 3614.9 秒不再增长**（真工作的话 CPU 会涨）——即 `scan()` 里的**网络调用没有超时，任务永久挂住**。
而 (d) 原判据把 `State=Running` 一律打印成「⏳ 正在运行」**放行** ⇒ **"启动过"和"跑完了"之间的那段黑箱没人管。**

**对策**：`Running` 且已运行超过阈值（默认 90 分钟；本项目最长正常任务约 30 分钟）判 **❌ 疑似挂死**，
阈值可用 `VERIFY_RUNNING_MAX_MIN` 覆盖。
**★并且当场做了会触发的验证**（造一个 `sleep 900` 的假任务 → 报 `❌ 已运行 2 分钟仍未结束`），
不是又写一条从没失败过的检查（FM-23 的教训）。

**教训**：**"进程还活着"不是存活判据，"它这次跑完了且返回 0"才是。** 对无人值守任务，
必须同时看三样：**返回码 / 最近运行时间 / 已运行时长**。缺任一样，就有一类死法能藏进去。

## FM-28 ★★ PowerShell 5.1 的两个「中文坑」：一个让远程脚本莫名崩，一个让中文静默变乱码

**症状**：同一批数据拉取任务里**同时**踩上两个，**表现完全相反**：
- **坑 A（高声崩）**：远端 Python 读 PowerShell 存下的 JSON，**RC=1，且只打印了崩之前那一行**，
  该输出的中文全没有 —— 看起来「莫名其妙崩在半路」，**没有任何指向原因的线索**。
- **坑 B（静默错）**：JSON 能读、字段能对上，但中文全是 `ç§æ¤ä¸ä¸æé`（「种植业与林业」的乱码形态）——**不报错**。

**根因（两条独立、同源：PowerShell 5.1 的编码默认值）**：
- 坑 A：`Set-Content -Encoding UTF8` 在 PS 5.1 **会写 BOM**（`EF BB BF`），
  Python `json.load(open(..., encoding="utf-8"))` 遇 BOM 直接抛异常。→ 改 `encoding="utf-8-sig"` 一次通过。
- 坑 B：`Invoke-RestMethod` 在响应 `Content-Type: application/json` **不带 charset** 时按 **Latin-1** 解码
  UTF-8 字节 ⇒ 双重编码乱码。

**★怎么抓到的（这步比结论值钱）**：
1. 坑 A：脚本「跑到某一行就停」——**只看它停在哪一行输出之后**，就锁定「崩在读文件」，
   比瞎猜快得多。**远端脚本静默半途崩，先数它落在哪一行后面。**
2. 坑 B：用**第二实现对账**（闸门⑨）——同一个接口改用 Python `urllib` 抓，
   原始字节显示 `"name": "国投丰乐"` **完全正确**且无 `\u` 转义 ⇒ 排除 Python、锁定 PowerShell 侧。
   **不做这一步，就会跑去改本来没错的那半边代码。**

**对策**：
1. Python 侧一律 `utf-8-sig` 读（同时吃有 / 无 BOM）。
2. **别让 PowerShell 碰中文 JSON**：抓取直接用 Python（`urllib` + `read().decode("utf-8")`）。
   必须用 PS 时：读 `[Text.Encoding]::UTF8.GetString((Invoke-WebRequest -Uri $u -Headers $h).Content)`，
   写 `[IO.File]::WriteAllText($p,$s,(New-Object Text.UTF8Encoding($false)))`（`$false` = 不写 BOM）。
3. 事后补救：`s.encode("latin-1").decode("utf-8")`（解不了的保持原样）——本例一次修回 **10,234 个名字**。
4. **加自检**：跨机产物落地后，抽样打印一个**已知答案**的中文字段（本公司名 / 行业名），肉眼可判。

**教训**：**「对方 shell 的默认编码」是跨机数据流上最容易被忽略的一层**；
这两个坑**可见度相反**（一个高声崩、一个静默错），**只防一个等于没防**。
与 FM-15（一个 BOM 废掉整台机器出站 ssh）是同一家族 —— 4 个月内第三次在 BOM 上栽。

## FM-29 ★★★ 校验器把自己排除在外：**唯一配错的那台机器，正好是它 ssh 不上的那台**

**症状**：`verify-live.sh` 跑完打出 **`old_origin=0`**，看起来"没有任何机器指向旧仓"。而真实情况是：
**本机（yuzhangyuan）的 `origin` 正指着已弃用的旧仓** `100.71.88.47:shared-git.git`，
与机群新镜像 `E:/myainet-shared-git.git` **分叉成两条历史线**（共同祖先 `117581a`，本地独有 8 条 / 新镜像独有 13 条），
**两条线都在活跃写入、互相看不见，持续了至少一天**，而所有校验都显示健康。

**根因（三层叠在一起）**：

1. **校验器通过 ssh 检查"包括自己在内"的每一台**。`NODES` 表里有
   `100.75.216.97|yuzhangyuan|...`，循环体一律走
   `ssh $SO Administrator@$H "powershell ... -EncodedCommand ..."`。
2. **本机 ssh 不到自己**：本机 `~/.ssh` 里只有 `id_ed25519`，而
   `authorized_keys` 里没有它（sshd 在跑，纯粹是不认这把钥匙）；
   脚本还固定 `-i $HOME/.ssh/id_dsh_mobile`，**该文件在本机根本不存在**。
   → `ssh` 失败 → `hh` 为空 → 判 `UNREACH`、`bad++`、**`continue`**。
3. **★致命的一步**：`old_origin` 的判定（`case "$oo" in *shared-git.git) ...`）**写在 `continue` 之后**。
   本机既然 `continue` 了，它的 `origin` **从来没有被判定过一次**。
   于是 `old_origin=0` 不是"检查通过"，而是"**这台机器压根没检查**"。

**★为什么这个坑特别毒：「跳过」和「通过」在输出上长得太像**

- `UNREACH`（离线或 ssh 失败）**是响的** —— 它会打印、会 `bad++`、会 `exit 1`。
- 但**人已经把 `UNREACH` 归类成"网络抖动"这种可容忍噪声**了（本网反复有过 ping 不通不代表连不上的经验），
  于是看到 `UNREACH` 就跳过，不会想到 **"这台机器的 origin 根本没查过"**。
- **输出里没有任何一句话说"那台机器有指标没被校验"**。校验器只报它查到了什么，从不报**它没查到什么**。

**★怎么抓到的（这步比结论值钱）**：

1. **不信单侧指标**。看到 `old_origin=0` 之后先去读 `.git/config`，发现
   `origin = Administrator@100.71.88.47:shared-git.git`，而同步脚本 fetch 的是
   `E:/myainet-shared-git.git` —— **两个路径根本不是同一个仓**。
2. **逐个镜像比 tip**（`git ls-remote <每个镜像> refs/heads/master`）：
   `ab7bc65`（旧）vs `9944cdf`（新），`git merge-base --is-ancestor` 返回非 0 ⇒ **真分叉**，不是"落后"。
3. **不要只看 `origin/master`**：`git fetch origin` 成功、`git status` 干净、`git log` 正常，
   因为 `origin` 指的就是那个**正在正常服务的**旧仓 —— **"不报错"和"对"是两件事**。

**对策**：

1. **校验器必须能校验自己**：节点目录在本地存在（`[ -d "$DIR/.git" ]`）就**本地直查**，
   **绝不允许 ssh 回环**。`verify-live.sh` 已改为此形态，并在输出里标出 `[local]` / `[ssh]` 与
   `self_checked_locally=N`。
2. **"跳过"必须在输出上与"通过"区分开，并计入退出码**（`UNREACH` 要能一眼看出是"没校验"而不是"校验过了"）。
3. **同一形态会第二次出现**：`shared-sync.sh` 也往 `100.75.216.97:D:/myainet-shared-git.git` 走 ssh 推 ——
   同样必失败。改为：镜像路径在本地存在就直接用本地路径（`.ps1` 版早有 `$LOCAL_BARES`，`.sh` 版漏了）。
4. **部署副本不许手工拷贝**：计划任务跑的 `C:\Users\Administrator\shared-sync.ps1` 是技能脚本的
   **手工拷贝**，且已与技能源漂移（根副本 v3 / 技能 v4）⇒ 修技能**不生效**。
   改为**薄包装**：只定位 `_shared`，把活交给技能里的唯一实现，并透传退出码。
5. **失败必须进退出码**（同 FM-22）：`shared-sync` 原先最后一行是 `echo`，**恒 exit 0**，
   连续输出 `state=DIVERGED pushed_remote=0/3` 而计划任务 `LastTaskResult=0` —— 故障在绿灯下躺了一整天。

**教训**：**"校验器自己"是覆盖面里最容易被漏掉的一格** —— 因为人本能假设"我就在本机上，我当然是好的"。
而**配置错误最可能发生的恰恰是本机**：别的机器都是照模板部署，**本机是被人手改的那台**。
这是 **FM-23（故障长在你没校验的地方）的最极端形态 —— 故障长在校验者身上**。
配套记住：**校验器只报"我查到了什么"，从不说"我漏了什么"；所以覆盖面必须跟着"实际在跑的东西"走，
而"正在跑这个校验器的那台机器"永远在覆盖面之内。**
