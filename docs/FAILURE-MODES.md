# 故障模式库（全部来自真实事故）

> 本文件是这个项目**最值钱的部分**。下面每一条都是真实发生过的，不是推演。
> 造这套共享层的人踩过的坑，你不必再踩一遍。

---

## FM-01 ★★★ 半截迁移：能推、拉不到，且**没有任何报错**

**症状**：主控机推到新镜像显示成功（`pushed_remote=2/3`），但某台机器的活副本**永远收不到新内容**。
`git log` 里找不到主控推的 commit。

**根因**：迁移只做了一半 —— 建好了新镜像仓 + 写了同步脚本，**但没有改各机活副本的 `git remote origin`**。
那台机器的 origin 还指着**旧的单源仓**。它的同步任务照样在跑、照样在推，所以一切"看起来正常"。

**为什么可怕**：**方向是单向的**。机器 → 镜像的推送能走，镜像 → 机器的拉取不走。
两个方向各自"成功"，合起来是断裂，而**没有任何一方会报错**。

**对策**：
1. 迁移必须**成对**：建镜像 + **改所有消费方的 origin**。
2. 同步脚本**只报推送侧是不够的** —— 必须加 `verify-live.sh` 逐台校验活副本 HEAD。
3. 把"活副本是否真的更新"变成**可检测事实**，而不是信念。

**教训**：`pushed_remote=2/3` 这种**单侧指标**会被所有人读成"同步好了"。
**只测了一半的链路，却当成全链路** —— 这是隐形态故障的标准剧本。

## FM-02 ★★★ 编号撞号：多机并发分配同一个 ID

**症状**：两台机器各自创建了 `mem-0212.md`，内容完全不同（一台写 ERP、一台写量化）。
合并时 8 个文件全部冲突。

**根因**：编号按「**数本地 INDEX 最大值 +1**」分配。每台机器只看得到**自己那条线**，
看不到别人已经占了哪些号 —— 并发下**必撞**。

**历史**：同一类事故发生过至少两次（`mem-0184` 撞号、`mem-0212–0219` 撞号）。

**对策（三层，建议全上）**：
1. **分配器**：`next-mem-id.sh` 跨**所有可达镜像**取最大编号 +1（禁止数本地）。
2. **结构消除**：per-agent 时间戳 inbox 作为唯一写入通道（`inbox-submit.sh`），
   由**唯一的 promoter** 分配正式编号（`promote-inbox.sh`）。文件名天然不冲突。
3. **守卫**：`hooks/pre-commit` 拒绝引入重复编号的提交。

**教训**：**架构解决不了多写者的编号冲突，只能靠"唯一分配点"或"结构上不共享命名空间"。**

## FM-03 ★★ 单点仓：一台机器挂掉，全网读写全停

**症状**：唯一的 bare 仓宿在 A 机。A 机一挂，五台机器**推不进也拉不动**。

**对策**：建 N 个互为镜像的 bare 仓，每个节点都能读写任意一个。
**关键**：镜像仓必须放在**数据盘**，不能放系统盘 —— 系统崩了镜像跟着一起没。

**教训**：可用性和一致性是一对取舍。**多副本买的是可用性，校验买的是它的一致性。**

## FM-04 ★★ 各机活副本有未提交改动 → 拉取被挡

**症状**：`git pull` 报 `Your local changes would be overwritten` 或
`untracked working tree files would be overwritten`，拉到一半失败，活副本变成 17 个脏文件。

**对策**：拉取**之前**先 `git stash push -u -m "autofix-<时间戳>"`
（`-u` 连未跟踪文件一起收），拉完**不自动 pop** —— 让那台机器自己决定何时恢复。
**永远不要**用 `git checkout .` / `reset --hard` 去"清理"别人的未提交工作。

**教训**：自动化同步脚本必须假设**工作区是脏的**，并且**保命优先于干净**。

## FM-05 ★★ 单侧比对：PowerShell 输出带 `\r` 导致校验假失败

**症状**：写好的活副本校验脚本，**所有机器全部报 STALE**，但人工一看 HEAD 都一致。

**根因**：Windows PowerShell 的输出行尾是 `\r\n`。ssh 管道里取到的值是 `"4ccf20a\r"`，
和 `"4ccf20a"` 字符串比对**永不相等**。

**对策**：跨平台取文本一律 `tr -d '\000\r'`。

**教训**：**校验脚本本身也会说谎。** 上线校验器时，必须先拿"已知正常"的场景验证它**不误报**。

## FM-06 ★ 子串误判：新名字包含旧名字

**症状**：origin 判断逻辑把所有机器都标成"仍指向旧仓"。

**根因**：旧仓叫 `shared-git.git`，新仓叫 `myainet-shared-git.git` ——
**新名包含旧名子串**。用 `case "$url" in *shared-git.git)` 先匹配，新仓也被命中。

**对策**：`case` 分支**先匹配更具体的模式**（先判 `*myainet-shared-git.git`），
且不要用 `[ "$x" != *glob* ]` —— **`[ ]` 不做通配符匹配**，那是个静默恒真的表达式。

## FM-07 ★ 前导零被当八进制

**症状**：编号分配器算出 `NEXT=mem-0152`，而实际最大编号是 `0227`。

**根因**：bash 的 `$((max+1))` 把 `0227` 按**八进制**解释（=151），加一得 152。

**对策**：算术前强制十进制：`$((10#$max + 1))`。

---

## FM-08 ★★ 冲突标记被当成"已解决"提交进去

**症状**：仓库里出现带着 `<<<<<<<` / `>>>>>>>` 的 Markdown 文件。

**根因**：`git add -A` 会把**仍含冲突标记**的文件标记为已解决，然后就能提交了。

**对策**：提交前扫一遍冲突标记（`check-integrity.sh` 内含此检查）；
能用 `git add <具体文件>` 就不要用 `git add -A`。

---

## FM-09 ★ 长任务挂在 ssh 会话上，会话一断任务就被回收

**症状**：远程起的长任务（几十分钟）跑一半就没了，日志停在中间。

**对策**：长任务要么**用 ssh 前台持有**（并由调用方后台化），
要要么**注册成计划任务**（`schtasks`）让它在机器上独立存活。
**不要**用 `Start-Process` 起 detached 子进程 —— ssh 会话结束时它会被回收。

---

## FM-10 ★ 只改文档没改消费方：约定写在纸上了，机器不知道

**症状**：协议文档里明明写了"各机 origin 指向新镜像"，但没人执行，于是 FM-01 发生。

**对策**：**能被机器校验的规则**才写进文档；否则给一个**一键脚本**并把它的输出接到同步流程里。

**教训**：文档不是约束，**可执行的校验才是约束。**

## FM-11 ★★★ 「索引写了，文件忘了」—— 悬空索引活了 8 天没人发现

**症状**：`INDEX.md` 里有 `mem-0130` 一行（内容完整、看着正常），**但 `memory/mem-0130.md` 文件从来不存在**。
全库浏览、全文检索都正常，**没有任何地方会报错**。

**根因**：提交时只 `git add` 了 `INDEX.md`，忘了 add 那个新建的条目文件。
一次真实的提交（`d70695e`）就这样：`memory/INDEX.md` + `DAILY/...` + `METHOD_LAWS.md` 三个文件进去了，
**条目本体漏在外面**。

**为什么危险**：它看起来"一切正常"。索引行的内容还在，所以**连读的人都发现不了** ——
直到有人真去 `open` 那个条目。**这是纯静默的数据丢失。**

**对策**：`check-integrity.sh` 的 §4 双向比对（INDEX ↔ 目录）。
**本次就是它抓出来的** —— 挂了 8 天的悬空行，体检一跑就现形。

**恢复**：内容往往没真丢 —— 它可能同时落在 `DAILY/`、`METHOD_LAWS.md` 或别的已提交文件里。
**先去 git 历史里找，再决定是重建还是删行。**

## FM-12 ★★★ 规则写成了文档 ≠ 规则存在（本项目诞生的真正原因）

**时间线**（真实事故的两次发生）：

| 时间 | 事件 |
|---|---|
| 2026-09-20 | 写 `mem-0128` 前没查远端编号 → 撞号 → rebase 冲突 → `git add -A` 把冲突标记提交进共享层（`mem-0130` 记录） |
| 2026-09-20 | **制定了方法律 #44/#45**："写记忆前必须 pull 并取远端 max+1"、"`git add -A` 会静默提交冲突标记" |
| **2026-09-28** | **同类事故原样复发**：写 `mem-0212–0219` 前又没查远端编号 → 与另一台机器的 `mem-0212–0219` **全部撞号**（8 条文件冲突） |

**根因**：`#44/#45` 当时**只写成了文档**。文档不会拦住任何事 ——
**8 天后没有人记得它，包括写文档的那个 agent 自己。**

**对策（本项目的存在理由）**：把每一条规则都变成**机器能判定的检查**：

| 规则 | 文档形态（无效） | 可执行形态（有效） |
|---|---|---|
| 写前取号 | 方法律 #44 一段话 | `next-mem-id.sh`（跨镜像取 max+1） |
| 别提交冲突标记 | 方法律 #45 一段话 | `check-integrity.sh` §3 + `hooks/pre-commit` |
| 索引进文件 | 无 | `check-integrity.sh` §4 双向比对 |
| 所有机器都同步了 | 无 | `verify-live.sh` |

> **文档不是约束，可执行的校验才是约束。**
> 如果你正打算把一条规则写进 README 然后收工 —— 请先问：**有没有一个脚本，能在违反时让人当场撞墙？**

## FM-13 ★★★ 安装器"假成功"—— 本项目的安装脚本自己犯了这个病

**症状**：`install-hooks.sh` 打印 `HOOK=OK`，但钩子**根本没装上**，后续提交畅通无阻。

**现场**：
```
cp: cannot create regular file '.../.git/hooks/pre-commit': No such file or directory
chmod: cannot access '.../.git/hooks/pre-commit': No such file or directory
HOOK=OK                      ← 仍然报成功
```

**根因**：脚本 `cp` 之后**没有检查退出码**，直接打印了成功。
（触发条件：某些 git 环境 `git init` 不创建 `.git/hooks/`，
本例就是 `templates not found` 导致 hooks 目录缺失。）

**为什么这条特别值得记**：**这个项目的存在就是为了消灭"失败却报成功"** ——
而**它自己的安装脚本犯了同一个病**。这恰好说明这类 bug 有多顽固：
它不是"粗心"，而是**"我没有验证我声称的结果"**这个习惯。

**对策（三件套，缺一不可）**：
1. `mkdir -p` 目标目录（别假设它存在）；
2. **每一步检查返回值**，失败即 `FAIL` 退出；
3. **装完必须回读验证**（`[ -x "$HOOKDIR/pre-commit" ]`）——
   不能只信 `cp` 的退出码，更不能什么都不信就打印 OK。

> **凡是打印"OK / 成功 / 已同步"的地方，都必须有一条"回读验证"紧跟其后。**
> 没有回读的成功报告，就是下一次 FM-01。

## FM-14 ★★★ 一枚明文 Token 在共享层里躺了 19 天，没人发现

**症状**：一个技能文件里**硬编码着 GitHub Token**。它随共享层同步到 5 台机器，
**没有报错、没有告警、没有影响任何功能** —— 直到有人为了别的事去翻那个文件。

**事故经过**：
某技能为了"一键发布到 GitHub"的便利，把发布用的 Token 直接写进了 HTML 的默认值里
（输入框 `value=` 和 JS 常量各一处）。Token 权限是 **`repo` 全仓**，
意味着它能读写该账号下**所有**仓库，包括一个私有仓。

**为什么它比想象中危险**：
1. **共享层是会被复制的** —— 它躺在那里，跟着镜像走到每一台机器。
2. **它在 git 历史里** —— 就算删掉文件里的那行，**历史里那串依然可读**，
   所以"删文件"根本不是修复。
3. **它是"便利"引入的** —— 不是为了偷懒，恰恰是**为了功能好用**。

**唯一的正确修复**：**轮换（revoke + 新建）**。文件清理只是附加动作。

**对策（三层，已全部落地）**：
1. `check-credentials.sh` —— 扫描明文凭据（GitHub/AWS/Slack/OpenAI/私钥/通用 `token=` 形态），
   命中即红色输出**并自动脱敏**，退出码非零。
2. 接进 `check-integrity.sh` §6 —— **体检就会带出来**。
3. 接进 `hooks/pre-commit` —— **提交当场被拒**。

**教训**：
> **"方便"是最常见的凭据泄露路径。**
> 任何"预填好、直接点就能发"的设计，都要问一句：**这里填的是不是密钥？**
> 而且 —— **密钥一旦进过版本控制，轮换就是唯一解**，别再想着删文件。
